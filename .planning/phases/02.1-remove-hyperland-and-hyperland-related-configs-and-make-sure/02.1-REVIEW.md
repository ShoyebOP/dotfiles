## Critical Issues

### CR-01: Committed plaintext API key in env.nu

**File:** `nushell/.config/nushell/env.nu:56`
**Issue:** The file contains a hardcoded live secret,
`$env.MISTRAL_API_KEY = "EXSu4QEIVkek7wjARerL5jdzZHfae0mF"`, committed to the repo.
This phase modified `env.nu` (removed the Hyprland launch block) but left the key in
place, so the secret ships in every clone. Anyone with read access to the repo (or
its history) exfiltrates a working credential. `AGENTS.md:90` acknowledges it only as
"Secret-like env ... see CONCERNS.md" — acknowledgement is not remediation.
**Fix:**
```nu
# Delete line 56 from env.nu entirely. Machine-local secrets belong in a
# gitignored override sourced only if present, e.g. in config.nu:
# if ("~/.config/nushell/local.nu" | path exists) { source ~/.config/nushell/local.nu }
```
Then rotate the exposed key (it is compromised the moment it was pushed) and purge it
from git history (`git filter-repo` / BFG), since deleting the line alone leaves it in
history.

## Warnings

### WR-01: reverify_deps skips the tick filter when SELECTED_DEPS is empty — false hard failure on unticked deps

**File:** `setup.sh:352-356`
**Issue:** `reverify_deps` treats an empty `SELECTED_DEPS` as "no selection" and
verifies the *unfiltered* dep list:
```bash
if [[ ${#SELECTED_DEPS[@]} -eq 0 ]]; then
    filtered=("${deps[@]}")   # deps came from get_deps, itself unfiltered (see WR-02)
```
`SELECTED_DEPS` is legitimately empty when the user ticks only non-toolchain rows
(`nushell`, `alacritty`, `keyd` — none of which are in `ALL_TOOLCHAIN`) and `stow`
is already installed (so `_toolchain_ensure_stow` does not re-add it). Reproduced:
with `SELECTED_PACKAGES=(nushell alacritty keyd)` and `SELECTED_DEPS=()`, the code
takes the unfiltered branch. Consequence: after installing exactly what the user
ticked, reverify demands every unticked toolchain dep too and exits 1 with `Error:
Still missing dependencies after install`, aborting an otherwise correct install.
**Fix:**
```bash
# Always filter; an empty SELECTED_DEPS is a valid tick-everything-off selection.
if ! mapfile -t filtered < <(filter_deps_by_selection "${deps[@]}"); then echo "Error: failed to filter deps for re-verify" >&2; return 1; fi
```

### WR-02: get_deps conflates "empty selection" with "no selection" — unfiltered bypass

**File:** `setup.sh:211,236-238`
**Issue:** `get_deps` applies the tick-authoritative rule only `if [[
${#SELECTED_DEPS[@]} -gt 0 ]]`, else returns the full mode set unfiltered.
Reproduced: with `SELECTED_DEPS=()` the function returns all 15 deps for
`arch/local` regardless of ticks. The install path in `main` is accidentally saved
by a second `filter_deps_by_selection` call, but any direct caller (tests, future
code, `reverify_deps` via WR-01) silently gets the unfiltered set — unticked means
"install everything". An empty array must not mean "no filtering".
**Fix:** Track "selection active" explicitly (e.g. a `SELECTION_ACTIVE` flag set by
`_split_unified_to_selected` / `_unified_apply_presets`) instead of overloading
array emptiness, and filter whenever the flag is set.

### WR-03: ~549 lines of dead legacy checklist code left defined but uncalled

**File:** `setup.sh:943-1491`
**Issue:** `prompt_checklist`, `prompt_toolchain_checklist`, `checklist_gum /
_whiptail / _dialog / _fzf / _read`, and `toolchain_gum / _whiptail / _dialog /
_fzf / _read` are never called — `main` only calls `prompt_unified_checklist`
(lines 1882, 1893). The SUMMARY admits this as "minimal diff", but it leaves 27% of
the file as dead weight carrying its own latent quirks (e.g. the contradictory
`list_height` clamp at lines 1021-1022 / 1079-1080 that always forces 7). Every
future ladder fix must now be made in two places, and readers cannot tell which
checklist is real.
**Fix:** Delete lines 943-1491 (the legacy two-page ladder) and the stale comment at
line 1500 referencing `prompt_checklist`. If a rollback reference is wanted, the git
history already preserves it.

### WR-04: sudo executed inside the DRY_RUN uninstall preview

**File:** `setup.sh:837-843`
**Issue:** The `DRY_RUN` branch of `run_uninstall` runs `sudo stow
--dir=... --target=/ --no --verbose --delete keyd` for real. `--no` avoids writes,
but executing `sudo` during a "zero writes" preview still prompts for a password,
updates the sudo timestamp, and crosses the privilege boundary the dry-run promise
exists to avoid. The install-path preview (`preview_selection`, lines 427-433)
correctly runs only unprivileged `stow --no`.
**Fix:**
```bash
echo "[DRY RUN] Would run: sudo stow --dir=\"$SCRIPT_DIR\" --target=/ --no --verbose --delete keyd"
# Do not execute sudo under DRY_RUN; mirror the install-path preview (no sudo call).
```

### WR-05: Uninstall offers `apt remove keyd` on Debian — contradicts the D-06 "never reaches apt" invariant

**File:** `setup.sh:665,679-687,701-710`
**Issue:** This phase carefully keeps `keyd` out of every apt path on Debian
(`prompt_debian_keyd_notice`, the `install_keyd_privileged` early-skip, the preview
mirror). But `offer_system_package_removal` builds a family-independent
`_allowed=("${ALL_TOOLCHAIN[@]}" alacritty keyd)` list, so on Debian-family the
dry-run preview prints `[DRY RUN] Would run: sudo apt remove -y keyd` and the live
path attempts it (failing into a warning) for a package that was by design
manually built from `rvaiya/keyd` and never apt-managed.
**Fix:** Make the allowlist family-aware — exclude `keyd` on `debian` (it was never
installed via apt), mirroring the install-path gate:
```bash
local -a _allowed=("${ALL_TOOLCHAIN[@]}" alacritty)
if [[ "${FAMILY:-}" != "debian" ]]; then _allowed+=(keyd); fi
```

stale pointers that actively misdirect agents reading this file for ground truth.
**Fix:** Rewrite the cited rows to the unified installer (`setup.sh`,
`setup.sh --uninstall`, `setup.sh --dry-run`), or delete rows describing the
removed dual-bootstrapper architecture.

### WR-07: Lowercased `selection:` preview line games the phase's own Selection-count audit

**File:** `setup.sh:413`
**Issue:** The SUMMARY (02.1-02, deviation 1) records that `preview_selection`'s
`Selection:` line was lowercased to `selection:` solely so that `grep -c
'Selection'` returns 1. That makes the verification gate pass by case-sensitivity
luck rather than by design: any future `grep -i`, doc audit, or second legitimate
`Selection` line silently breaks or falsely satisfies the gate, and the UI now shows
inconsistently-cased output (`selection:` vs `Selection`/`Final selection`
elsewhere).
**Fix:** Keep one canonical header (e.g. `Selection:` in the unified dispatcher
output) and remove the duplicate line from `preview_selection` instead of changing
its case — or assert on the header text (`=== Unified Selection`) rather than a
case-sensitive substring count.

## Info

### IN-01: Tick-authoritative rule is implemented twice and applied twice

**File:** `setup.sh:223-238,250-272,1901-1904`
**Issue:** The same drop-unticked-stow-row rule exists inline in `get_deps` and
again in `filter_deps_by_selection`, and `main` applies both in sequence
(`get_deps` filters, then `filter_deps_by_selection` re-filters). Idempotent today,
but the two copies (including duplicated comments) can drift — a fix to one will
not obviously need mirroring in the other.
**Fix:** Remove the inline filter from `get_deps` (keep it a pure family/mode dep
source) and let `filter_deps_by_selection` be the single enforcement point.

**File:** `setup.sh:1205-1207`
**Issue:** The toggle branch prints `Final selection: ...`, then `6 packages
offered`, then `Final selection: ... (offered 6, selected N)` — the first line is
redundant noise in pre-write output.
**Fix:** Drop the line 1205 echo; keep the audit-suffixed form.

### IN-03: README sudoers example hardcodes username `shoyeb`

**File:** `README.md:116-120`
**Issue:** `shoyeb ALL=(ALL) NOPASSWD: ...` breaks copy-paste for every other user
and invites a misconfigured sudoers edit (a syntax error in sudoers can lock out
sudo). Pre-existing, not introduced this phase.
**Fix:** Use a placeholder (`<your-username> ALL=(ALL) ...`) and add the standard
`visudo -c` validation reminder after editing.

### IN-04: Uninstall DRY_RUN keyd preview lacks the install path's Termux/Debian gates

**File:** `setup.sh:826-844` (cf. `415-425`)
**Issue:** The install preview skips privileged keyd output on Termux and on Debian
without a keyd binary, but the uninstall dry-run unconditionally prints (and, per
WR-04, executes under sudo) the privileged `--delete` preview. Harmless output
today (`stow --no --delete` of a never-stowed package just reports), but the two
previews disagree about the same machine state.
**Fix:** Mirror the Termux skip and Debian-no-binary skip in the uninstall preview
branch.
